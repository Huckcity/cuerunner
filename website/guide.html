Overview

Winslab is a cue stack for live operation. You build a list of cues, arm the ones you want, and fire them with GO. Everything is designed around two questions an operator asks mid-show: what runs next, and what just happened.

This guide covers Winslab 0.7 and later. It documents the application as it behaves today, including the rough edges listed under Known limitations.

The window

  1. Toolbar — the WinsLab menu (New, Open, Save, Save As, Recent, Settings), the workspace name with a dirty dot, and the add-cue buttons.
  2. Cue list — the running order. One row per cue, with duration, pre-wait, post-wait, and any auto-advance in the columns on the right.
  3. Inspector — settings for the selected cue. Tabs change with the cue type.
  4. Waveform / timeline — what the dock shows for the selected cue: the waveform of an audio cue, or the timeline editor for a timeline-mode group.
  5. Dock — the panels along the bottom share one space and open one at a time: the selected cue, the run log, the show monitor, the wireless panel and the script. The tabs across the top of the dock — Cue, Log, Monitor, Wireless, Script — choose, and the chevron on the right hides it.
  6. Transport bar — STOP, GO, PANIC, the running indicator and the selected cue.

macOS

Winslab is not code-signed for the App Store, so the first launch may warn about an unidentified developer. Downloads come from pub.winslabapp.com.

Free and Pro

The cue stack is free, and it is the whole of the free app: every cue type, the timeline, the waveform, the run log, workspaces and the demo show. WinsLab Pro is the rest of the show — the services that listen, the views the show is run from, the panels that read it, and the showfile's own history: reading what its saves changed, comparing it with another version, merging two people's copies, and handing it over as one file. Every Pro section in this guide is marked Pro.

Pro is unlocked with a license key: WinsLab ▾ → Settings… → License, paste the key, Activate. The key is checked on the machine it is entered on and nothing is sent anywhere, so a venue with no internet unlocks the same as any other, and going to air afterwards tells nobody anything. It is not tied to the computer, because checking that would take an activation server or an identifier collected before the sale; keeping one key to one machine is a matter of trust. The key is checked when the app starts, so a show that began licensed finishes licensed, and a key that has run out locks the next launch rather than the performance. The same tab deactivates it.

Show files are never affected by which half you are running. A workspace written with Pro opens on any machine with its scenes, its mic plot and its triggers intact, and saves back exactly as it arrived. Without a key the Pro surfaces show what they are and how to unlock them, the show services do not start, and a scene cue fired from the stack writes that it needs a license into the run log and lets the rest of the show carry on.

The demo workspace

WinsLab ships an example show with one cue of every type: a sequence group, a timeline group, audio with fades, MIDI, OSC, a network request, a script, and a stop cue. Open it from the WinsLab menu, or from the button on an empty cue list. It opens as an unsaved workspace, so Save asks where to put your copy instead of writing over the bundled file, and its audio is copied into the app's user data folder when it opens — which is the path its audio cues play from.

Unsaved changes

An amber dot next to the workspace name means there are unsaved changes. Closing the window, starting a new workspace, or opening another one asks to save first, with Save, Don't Save, and Cancel.

While there are unsaved changes, WinsLab also snapshots the show into the app's user-data folder every 30 seconds. If a session ends without saving — a crash, a force quit, a power cut — the next launch offers the snapshot back with Recover and Discard. Recovered work counts as unsaved, so the amber dot is still there until you save. Saving, discarding, or closing with Don't Save clears the snapshot.

Saving replaces the file in one step and keeps the previous version beside it as show.wlab.bak, so a save that fails part way through cannot leave a half-written show. If a save does fail — a read-only folder, a full disk — the reason appears in a bar at the top of the window, and the run log records it.

What the file remembersPro

Every save that changes the show writes a line into the file: who saved it, when, and what moved — the cues added, removed, edited and moved, and the settings that changed. WinsLab ▾ → Show History… reads those lines back, newest first, with the detail of each entry behind a disclosure.

A save that changes nothing writes the same bytes back and adds no line, which is what makes a showfile safe to keep in version control: a show opened, saved and closed without an edit is the same file. Bringing an older file up to this version's shape is a change to the file rather than to the show, so it is not recorded as an edit. A file remembers its last two hundred changes and lets the oldest fall off.

The history lives in the .wlab, so it survives being copied, emailed or handed over. It is written whether or not this machine is licensed — it is the show's own record of itself — and reading it in the app is part of Pro.

Comparing two versionsPro

WinsLab ▾ → Compare Show… takes another saved show and says what changed from it to the show on screen: the cues added, the cues removed, the cues edited with the fields that changed, the cues that moved, and the settings that moved with them. The file you pick is the older side, so read the heading as "what changed since this was written" — the version from last night's rehearsal against the one you are holding.

The comparison is about the show rather than about the machine: the audio file a cue plays is compared by the file's own name, so a show copied into another folder, or onto another machine, does not read as every cue having been edited.

Merging two people's workPro

WinsLab ▾ → Merge Show… merges another person's copy of the show into yours, and asks for the version the two of you started from. That third file is not bookkeeping: with two files alone, "I changed this" and "you changed it" look the same, and a merge that cannot tell them apart throws one person's work away.

A cue one side changed is taken. A cue both sides changed in different fields is put together. A cue both sides changed in the same field is a conflict: the merge keeps one side's value and names the conflict — the cue, both values, and whose was kept — rather than deciding quietly. The order is this show's, with the other side's cues placed among the neighbours they were added after, and groups stay together.

What a merge will not pretend to do is said rather than guessed: the audio file a cue plays is this show's, because the other copy resolved its media on the other machine; a cue whose group went away comes back at the top level; and each of those is listed in the report.

The merge writes a new file and leaves both inputs exactly as they were, so it is safe to try twice. The report's second button runs the same merge over the same two files again with the other side's choices for the conflicts.

Handing a show over as one filePro

WinsLab ▾ → Export Bundle… writes the show and every audio file it plays into one .wlabx: a zip holding show.wlab and a media/ folder, with the showfile pointing inside it. It opens in any file manager, and its bytes are a function of the show, so two exports of the same show are the same file. A file the show names that is not on this machine is reported rather than failing the export.

Import Bundle… asks where the show should live, unpacks it there and opens it: the audio is in the folder beside the showfile, so every cue plays without anything to relink. If the folder already holds files by those names, the app asks before replacing them. A bundle whose contents do not match the checksums it carries is refused rather than half-unpacked.

Moving a show between machines

An audio cue's file is stored twice: relative to the workspace folder when it lives inside it, and always as the absolute path it had at the last save. Copying the whole show folder to another machine — or another drive — keeps every cue pointing at its file, and a file that stayed behind while the workspace moved is still found by its absolute path. A file that neither of those finds is reported in the missing-media bar, and one press re-points every file that moved with it.

For a handover, or when the audio is scattered across a desktop and three render folders, Export Bundle… puts the show and every file it plays into one .wlabx instead. Copying only the .wlab — without its audio and without a bundle — still leaves audio cues pointing at paths that were never on the other machine.

Workspaces written by older versions are migrated on load: missing timing fields are filled in with defaults, the legacy autoContinue/autoFollow flags are dropped (Advance defaults to none), and old group childIds arrays become parent pointers. A stop cue from an older file gains waitForFade: false, and the retired per-output deviceId/channelPair fields are dropped.

# is the cue number and type icon. Name is the cue name, shown as untitled when empty. A group row's duration is derived from its children rather than stored: a timeline group ends at the furthest child, and a sequence group sums its children. Playlist and random groups fire on demand, so their length cannot be known and the column shows –.

Timing and advance

Every cue, whatever its type, has the same timing model on the Basics tab. It is worth understanding once, because groups, auto-advance, and the timeline all build on it.

FieldWhat it does
Pre-waitDelay before the cue fires. The row shows a pre-wait pill while it counts down.
Post-waitDelay after the cue finishes, before the next one may run.
DurationHow long the cue itself takes. Set directly for waits and fades, detected from the file for audio cues.
AdvanceNone, On start, or On end — see below.
Timeline offsetWhere the cue sits inside a timeline-mode group, in milliseconds from the group's start.
ArmedA disarmed cue is skipped by GO, and excluded from group playback.
NotesA free-text field for the operator. It never affects playback.

The order of a firing is always: pre-wait, then the cue runs, then post-wait, then the cue is finished.

Advance

None — the cue finishes and stops. The operator presses GO again.
On start — the next cue fires as soon as this one has started, so both run together.
On end — the next cue fires after this one completes, including its post-wait.

Auto-advance is what makes a cue stack playable as a sequence. With Advance set to On end for every cue, a single GO runs the whole show.

When you press GO, the selection moves to the cue that will be fired next, skipping over any cue that is about to fire itself. That way the highlighted row is always the next thing GO will fire.

Transport and keyboard

GO

Fires the selected cue. Space

STOP

Cancels every timer, stops all audio, clears all running state, and abandons work that is still in flight — a request or script that finishes afterwards cannot restart the show. Escape

PANIC

The same, with a 200 ms audio fade instead of a cut so it does not click, and it stops a running script. Shift + Escape

The running indicator at the left of the transport bar counts the cues currently in pre-wait, playing, or post-wait, and reads idle when nothing is running.

These keys are ignored while you are typing in a text field, so editing a cue name will not fire the show.

PANIC also comes from the application menu — Ctrl/Cmd + Shift + P — which silences the engine even when the window is not answering, and from a desk or a controller with a panic button of its own. See Panic from the hardware.

Waveform

Selecting an audio cue shows its waveform below the cue list, with the played part drawn in a lighter blue and a playhead while it runs. The part of the file the cue plays — its region — is drawn as a brighter band with a round handle at either end: drag the head or the tail to trim it, and the two halves of a split move together so the join stays a join. The header says what the region plays, with a reset that puts the whole file back. A cue trimmed of its silence is drawn for what it will play: the silence at the edges is shaded like the rest of the file the cue does not play, and the header reports the part that will be heard rather than the region as it was set.

Click anywhere on the waveform to place the cursor there; if the cue is already playing, the click seeks to that point instead. The cursor is the place a split cuts at — choose Split here from the cue's right-click menu — and it belongs to the cue it was placed on, so it is not drawn on the next track you select. The − and + buttons zoom from the whole file in to a second of it, keeping the cursor where it is on screen; Ctrl (or Cmd) and the wheel does the same at the pointer, and the wheel alone pans along the file.

Accepted file types are mp3, wav, ogg, flac, m4a, and aiff in the file picker; the drop zone also accepts wave, aif, aac, opus, and wma.

MIDI cues

A MIDI cue sends a list of messages to one output port. Pick the port from the MIDI tab — the list is read from the system, and the refresh button re-reads it. If you leave the port unset, the cue uses the Default output chosen on the MIDI tab in Settings. If no ports are found, the field becomes a text box you can type a port name into.

MessageFields
Note OnChannel, Note, Velocity (0–127)
Note OffChannel, Note, Velocity (0–127)
CCChannel, Controller, Value (0–127)
Program ChangeChannel, Program (0–127)
SysExHex payload bytes; the F0/F7 framing is added for you

Messages are sent in order, all at once, when the cue runs. Channels are 1–16. On Linux, MIDI needs the native module built against ALSA — see Install.

Show control cues

A show control cue tells another console what to do: the lighting desk on the next GO, an automation system on a reset, a playback machine on a load. It sends MIDI Show Control, so the cue it names is the receiving desk's own — its numbering, not a cue number of ours.

FieldNotes
CommandGo, Stop, Resume, Load or Reset. Load puts a cue in standby without running it, and Reset carries no cue data — the two fields below are not offered for it.
ForWhat kind of equipment the command is addressed to: Lighting, Sound, Machinery, Video, Projection, or Everything.
DeviceThe receiving console's Show Control device ID, 0–127. 127 is the all-call every device has to answer, which is what a new cue sends; both this and For have to match before a console acts.
CueThe cue number on that console, as its operator would type it — 12, 5.4. Empty means the next cue in its list.
ListThe console's cue list. Empty is whatever it has open.
SendTo the show's desk goes out on the connection Show Settings → Channels already has, which is how a cue list on the sound desk is reached with no cable from this machine; To a MIDI port goes out of a port of this computer, which is how the lighting console at the end of an interface is reached.

A cue with nowhere to go says so in the run log rather than reporting a send it did not make — including a show whose desk is driven over OSC, which carries addresses rather than MIDI Show Control.

The other direction is a trigger: a cue can answer a console's own command, matched on every field the console sent, or a button on the sound desk itself. See Triggers.

OSC cues

An OSC cue sends one message to host:port at an address, with a typed argument list. Each argument is an int, float, string, true, or false; changing an argument's type resets its value.

Winslab sends OSC but does not yet listen for it, so incoming OSC cannot trigger cues.

Wait cues

A wait cue holds the sequence for its duration. On its own it does nothing visible; its value is in a sequence, where it is the gap between two things — a scene change, a count for a stage call, or a delay before a network trigger.

Set the duration on the Wait tab. Add Advance > On end on the Basics tab if the cue after the wait should fire by itself.

Fade cues

A fade cue ramps another cue's volume or pan over a duration. Choose the target cue from the Fade tab; the list shows every other cue as number and name.

Stop cues

A stop cue halts a running cue: everything, or a single cue, either cutting instantly or ramping to silence first. Audio fades; a script cue is stopped and its run released, because a script runs on a worker of its own that no fade can reach. Aimed at a group it stops everything under it, however deeply the group nests, and the group does not carry on to its next child.

FieldNotes
TargetAll cues, one specific cue, or a group — which stops everything under it.
Fade outRamps the target to silence instead of cutting it dead.
Fade durationLength of that ramp.
Wait for fadeInert unless Fade out is ticked. When on, the cue stays open until the fade has finished sounding; when off, it completes as soon as it has stopped the target.

By default the cue completes as soon as it has stopped the target, so a following cue can run while the tail fades; tick Wait for fade to hold it open until the fade has finished sounding. PANIC does the same thing globally, with a fixed 200 ms fade.

Group cues

A group holds other cues. Children are stored flat in the list and shown indented under their group; collapse the group with the chevron in its row. Deleting a group deletes its children.

ModeBehaviour
SequenceRuns every armed child in order, then completes.
PlaylistFires one armed child per GO, so the operator steps through the group by hand. The group keeps the selection until the last child has fired, then hands it on to the next cue. STOP returns it to the first child.
RandomFires one randomly chosen armed child, then completes.
TimelineFires children at their Timeline offset, measured from the group's start.

Disarmed children are skipped in every mode, and a group with no armed children completes immediately.

Timeline mode

Select a timeline group and the timeline editor replaces the waveform. Each child is a block whose position is its offset and whose width is its duration. Drag a block horizontally to retime it, or set the offset numerically on the Basics tab. The zoom control steps through 5 to 800 pixels per second.

A dragged block snaps to the edges of the other blocks and to the start of the group, so runs of cues lock together end to end without pixel-perfect aim. A blue guide marks the edge a block has locked onto. The pull is measured in screen pixels, not milliseconds, so zooming in narrows it: at the fine zoom levels you can place a block within a few milliseconds by hand, and the Basics tab takes an exact offset.

Clicking the ruler seeks: the group stops, and playback resumes from that point, with audio and waits starting mid-way where they should. Cues that have already passed are not replayed — a network or script cue before the playhead will not fire again. The expand button in the timeline header gives the editor the whole window.

Network cues

A network cue makes an HTTP request when it fires, for triggering lighting desks, video servers, or webhooks. The show waits for the response, or for the timeout, before moving on — so a slow or unreachable target holds the cue.

FieldNotes
MethodGET, POST, or PUT.
URLThe full address, including the scheme.
TimeoutMilliseconds, 5000 by default. The request is aborted when it elapses.
HeadersAny number of name/value pairs. Add Header adds a row; the ✕ removes one.
BodySent for POST and PUT. Disabled for GET, which cannot carry one.
Requests come from the app window, so the target server must allow cross-origin requests. A server that does not return CORS headers makes the cue fail with Failed to fetch. A non-2xx response is reported as a failure in the log and the Last Run section, but the show still advances.

Script cues

A script cue runs JavaScript at a cue point, on a worker thread of its own — a script that never yields cannot freeze the interface. The script is an async function body, so await works and the cue holds the show until the script finishes. A script that throws is reported in the log and the cue still completes, so one bad script cannot stall a show.

The Timeout field is the longest the script may run, 60000 ms by default. A script that is still running when it elapses is stopped and reported as a failure; set it to 0 to let a script run for as long as it needs. STOP and PANIC also stop a running script, as does a stop cue aimed at it.

Helpers

HelperWhat it does
await shell(command, options?) Runs a system command and resolves { stdout, stderr, code, signal }. Options are timeout (milliseconds, 10000 by default), cwd, and env. Commands start in the workspace folder.
await include('path/to/file.js') Runs another JavaScript file and resolves what that file returned, so a helper file can hand back values. Each file is read and run once per cue, however many times it is included; an include inside an included file resolves relative to that file. A cycle — two files including each other — is reported as an error.
console.log(), console.error() Write to the run log, so output is visible without DevTools.

An example that calls a system tool and reports what it said:

console.log('house lights → warm')
const r = await shell('dimmerctl set 80')
console.log(r.stdout.trim())
Script cues are not sandboxed. They run in the app, with the same file and process access as the application itself, and the helpers above are their only way to reach it. A workspace file is executable code, so only open .wlab files you trust.

Reading results

Two places tell you what a cue did. The Last Run section at the bottom of every cue's own tab shows the outcome of that cue's most recent firing: when it started, how long it took, and the reason for any failure — the HTTP status and the start of the response body for network cues (cut off at 4000 characters with a truncation marker), the message for a script that threw or timed out, or the port an audio, MIDI or OSC cue could not reach.

A cue that could not do what it says is reported rather than passed over: an audio cue whose file is missing, a MIDI cue aimed at a port that is not there, and an OSC send that failed all mark the run as failed. Note that a MIDI or OSC cue can only report what the send itself did — OSC is UDP, so a message that leaves the machine and is never received still counts as sent.

The run log records every firing across the show. Open it with the Log tab in the dock.

Log lines are coloured by kind: cue lifecycle in the normal text colour, script and shell output in monospace, and failures in red. Each line carries the time, the cue it belongs to, and the message. Clear empties the log.

The log is a session history, capped at the last 500 lines, and a single script run emits at most 200 lines before it is truncated. It is not written to the workspace file, and it is not kept when the app closes.

In a packaged build there is no developer console, so the log panel is the only place to read script output. Running from source, the same failures also appear in the terminal as [renderer] … lines.

The show around the cue stackPro

A cue stack is only part of what is happening in the room. WinsLab also listens: it takes OSC and MIDI from the desks, tablets and cue lights around it, watches wireless transmitters against the mic plot, and notices when something on the network stops answering. Those are the show services, and the Monitor tab in the dock opens the panel that shows what they are doing.

The monitor

Two columns, left to right. Services is what is listening and what it is doing — a service that failed says why, and a restart button sits next to it. Devices is what is on stage or on the network, with the readings each one reports. What arrives rather than what is running goes to the run log, where every message the inputs carry is written with its sender and its arguments.

Alarms appear above the columns and are also written to the run log, so an alarm outlives the panel being closed. A failing service never stops the cue stack: a wireless poller that cannot reach its rack, or an OSC port another program is holding, degrades that one service and says so while GO keeps working.

What can be listened to

ServiceWhat it does
OSC inputListens for OSC on a port of its own (53000 by default) and publishes every message with its sender and arguments. A port another program holds is reported rather than taken.
MIDI inputOpens the input ports you choose (all of them if you choose none) and decodes what arrives. An interface that disappears mid-show is reported, because the cue that played a note down it will silently play nowhere.
WirelessPolls your receiver telemetry and joins it to the mic plot. See Wireless and the mic plot.
Network presenceBrowses the network over mDNS for devices that announce themselves — Dante endpoints among them — and reports one that leaves.
Every service is off or idle until it is asked for, except OSC input, which comes up on its default port so a desk can talk to a new workspace without any setup.

Panic from the hardware

Two messages the inputs above already carry are read as a panic, whoever sends them: OSC /winslab/panic (any arguments), and MIDI All Sound Off — controller 120 at value 0, on any channel of any port the MIDI input is listening to. A desk with a panic button, a controller with a spare key, and a network panic from another program all work without a cue being written for them.

They are acted on in the main process, where the engine is, rather than in the window: the fade starts whether or not the interface is answering, and the run log records who asked — [main] panic (osc): OSC /winslab/panic from 192.168.1.24:8000. The fade is the same 200 ms that Shift + Escape uses.

Wireless and the mic plotPro

The wireless panel answers the two questions asked most often in a radio-mic show: who is wearing which pack, and which one is about to die. The Wireless button in the dock opens it.

The plot

A pack has a label, the receiver channel it is patched to, and the performer wearing it. The panel sorts by trouble rather than by number: a pack at a critical battery first, then one that has gone quiet, then one that is low, with everything healthy below and unassigned packs at the bottom. A row shows the battery and RF as bars beside the numbers, the frequency, whether the channel is muted, and the performer's role.

The wording is deliberate. A pack with no channel assigned is unpatched — a patch waiting to be made, not an alarm. A pack that is assigned but has never reported is silent: the rack may still be booting, or the transmitter may be switched off. A pack that stops reporting for longer than the threshold is offline, and that is when it raises an alarm — including a pack the rack never reported at all, because the plot is the expectation.

Where the readings come from

WinsLab does not speak a receiver's own protocol. A source returns a JSON document with this shape, over HTTP or from a file on disk: 

{
  "channels": [
    { "id": "ulxd-1", "name": "Pack 1", "batteryPercent": 42,
      "batteryMinutes": 95, "rfDbm": -62, "audioLevel": 71,
      "muted": false, "frequencyMhz": 606.5 }
  ]
}

The field names are the contract: a bridge written against a receiver's own API only has to emit them, and any field a channel does not report is simply left out — the panel shows nothing for a reading that was never made rather than a zero. Add sources on the Wireless tab in Settings, where the service also reports what it is doing.

Demo rack loads a simulated twelve-pack show with a pack in trouble, one that is low and one that never reports, so the panel and its alarms can be seen without a receiver on the bench. It replaces the source list rather than adding to it, and it brings its own cast only when the plot is empty — a plot somebody entered is not the demo's to overwrite. The packs are plainly a simulation and not real hardware.

Entering your plot

Edit plot… opens Show Settings on its Mic plot tab: a pack is a label, the receiver channel it is patched to, and the performer wearing it. Channels are offered from what the wireless service is already hearing, so a patch is picked rather than typed from memory — but the field stays free text, because a pack that is switched off today is still part of tonight's plot. The performers the assignment picks from come from the Cast tab of the same dialog, where a performer is a name, a role, and the strip their mic is patched to.

Text fields commit when you leave them, so nothing is rewritten mid-word. Every change goes through the same operations the rest of the app uses, which is what makes the next part work without anything extra.

Swaps

Handing a pack to someone else — or taking it off them — is recorded as a swap: the pack, who it came off, who it went to, and when. A swap is written to the run log at the moment it happens and kept in its own list, so a quick change at 20:14 can be answered long after the fact. Removing a performer releases every pack they were wearing, and each release is a swap in its own right.

The report

Report reads the night back: for each pack, the performer, the lowest battery it reached and when, how many times it went quiet, and how many times it changed hands. The same text can be copied to the clipboard, which is what goes in the show file or the email about which packs need charging.

The report is read from the running session: the battery floor and the dropout count are kept by the wireless service as it polls, and the swaps are kept in the workspace. Closing the app ends the session, so copy the report before you do.

Thresholds and alarms

Alarms are raised on a crossing, not on every poll: a pack that sits at 8% for an hour says so once, and only says so again if it recovers and falls again. The defaults are a warning at 25% and critical at 10% battery, a warning below -75 dBm, and six seconds of silence before a channel counts as gone. All four are set on the Wireless tab in Settings, and they live in the workspace with the plot, so a show carries its own idea of what is bad.

The silence window is the one worth thinking about. Six seconds is long enough that a dropped poll does not read as a lost pack, and short enough to notice a transmitter that has actually died before its performer is halfway through a line. A show whose packs get switched off between scenes is normally happier with a longer window — thirty seconds is a common choice — because the row's colour already turns the moment the silence starts, and the warning is what is being held back, not the news.

The alarm names the performer because the plot says who is wearing the pack: "Pack 1 (Aldonza) battery critical — 6% left" is a sentence you can act on, where a channel number is one you have to look up.

TriggersPro

A cue usually fires when the operator presses GO. A trigger lets a message from somewhere else fire it: the lighting desk, a tablet, a footswitch, a show-control macro. Triggers live on the Basics tab, under the fields every cue shares.

OSC, MIDI and show control triggers

An OSC trigger is an address, matched exactly — /eos/cue/12/fire fires the cue it is on and nothing else. A MIDI trigger is a message on an input port: a note-on or note-off (any velocity), a controller (any value), or a program change. The value a desk sends is how it expresses itself, not which cue it means, so it is not part of the match.

A sound desk has no GO key and does not send show control, so a show driven from the desk is run from spare mute groups assigned to keys at the desk — see Scenes, and the desk — which the app reads as GO and BACK for the scenes. Anything else the desk transmits works too: a soft key or footswitch set to send a MIDI note transmits one on the press (soft keys are notes from C3 upward, one per key), and a scene recalled on the desk sends its bank and program change. Pick the desk's own connection as the device — it is named as address:port, and Learn fills it in for you — and the cue fires when that key is pressed.

A show control trigger is a console's own MIDI Show Control command: the command, what it was addressed to, the device ID, and the cue it names — every field matched, because a console going to cue 12 is not a console going to the next one. Pick the port the command arrives on, then Learn while the desk sends one, or type the fields from the console's own document. It is how a lighting desk's GO turns into the sound cue that follows it.

Learn is usually faster than typing: press it, then send the message from the desk, and the trigger is written from what arrived — the address, or the port, channel and message.

A trigger fires the cue the same way GO does: pre-wait, post-wait, advance and grouping all behave normally, and the log line says what fired it, so a triggered cue reads differently from one the operator fired. Disarming a cue stops its triggers too — that is what disarming is for.

Nothing about a trigger can interrupt the show: a cue that is already running keeps running, and a message that nothing answers to is shown in the monitor and otherwise ignored.

The script, and the tabletPro

Most operators keep the script open while they work. The Script tab in the dock opens it: the document, the cue that fires on each line pinned to it, and the line the next GO will fire from marked as the show moves.

Pinning cues to lines

Choose the file, then select a cue and click the number of the line it fires on. The line lists the cues pinned to it, and clicking the number again unpins. The line is stored on the cue, so the pins travel with the workspace — and a script that is replaced by a later draft keeps them, because a line number is a line number.

Following the show

The line of the cue GO would fire next is highlighted and scrolled into view. Scroll the document yourself and the follow releases, so reading ahead is not yanked back; the follow button returns to the show. A− and A+ set the size, which is remembered in the workspace.

The tablet

The companion serves a read-only view of the show — the running order, the next cue, what is running now, the script with the current line marked, and the recent alarms — to anything on the same network with a browser. There is nothing to install: open the address the Network tab reports, with the token on the end of it.

It is off until it is switched on, and it refuses every request that does not carry the token. Nothing on the companion can change anything: it is a window on the show, not a control surface. Anyone on the same network who has the token can watch, so treat it the way you would treat a script left open on the desk.

Scenes, and the deskPro

The part of a musical that a cue stack does not handle on its own is the mics: at the top of a number four people walk on, two others walk off, and the desk has to follow. A scene is who is open on stage. Recalling one tells the desk the difference.

The Scenes switch at the top right opens the view it all happens in: the same show as a grid, filling the window in place of the cue list, with the transport bar — GO, STOP, PANIC — exactly where it was. It is where the show is run, and where the scenes themselves are edited. Everything the grid is built from — the console, the cast, the mic plot — is set up once in Show Settings, and the grid carries no field for it, because a second way to edit the same thing is a second way to get it wrong.

Reading it

A filled cell is a mic that is open in that scene. The column of the scene the desk is set to is tinted and the rows it opens are brightened, which together answer the question asked most often in a radio-mic show: who is on right now? The first column is All closed — every mic the show drives, shut, which is what the desk wants between numbers — and it is a place the desk can be rather than a scene anybody builds. Each column after it is a name and two presses: → sends that scene to the desk, and the ✕ beside it removes the scene; how many mics a scene opens is the block of colour under it, so nothing spells it out. An ensemble row sits above the mics: one named group, and a cell per scene saying whether that scene applies it.

Following the show

A musical is wider than the window: thirty numbers at a readable width run several screens across. So the view follows the show instead of waiting to be scrolled — when a scene cue, a trigger or a press moves the desk to a scene, that column is brought to the left of the grid with the ones after it laid out to the right. A short number cannot leave the next scene off the side of the screen.

The header carries the same answer in words, in the one part of the view that never scrolls: now with the scene the desk is on, and next with the one after it in the running order. Before the show starts, now says nothing recalled and next names the opener. Scrolling by hand is left alone — the view moves when the show does, and not otherwise.

Editing it

Click a cell to open or close that mic in that scene. Add scene appends a column and the name is edited in the column header, where it is read. + Ensemble takes the mics that are open in the scene the desk is on and keeps them as a named group, applied to that scene from then on — the chorus that walks on together in the next number is one press rather than a row of them, and a member the scene closes anyway leaves the group reading as partly open rather than as a tick that lies. The rows are the performers; the strip each mic is patched to, and the DCA it opens, are set up once in Show Settings, so the grid carries no field for them.

A deleted scene is not gone: Ctrl/Cmd + Z puts it back where it was, with the mics it opens. The same undo covers the cues, the scenes and the whole of the show's setup — the console, the cast and the mic plot — so an edit made in either view is one press from being back.

Where it is set up

Show Settings, at the foot of the WinsLab menu, is the show's own setup — kept with the workspace rather than with the machine, in three tabs: Channels, Cast and Mic plot. Channels holds the desk: one connection for the whole show, OSC or MIDI, or no desk at all. OSC is one host, one port and an address pattern with {n} where a DCA's number goes — /dca/{n}/on unless the desk wants something else — and the line under it reads the pattern back as the first and last message the show will send, because a pattern and a port are easier to check as addresses than as a template. A MIDI desk is a port and a channel, and each DCA is a note, numbered from one the same way. A desk that serves MIDI on the network — an Allen & Heath SQ or Avantis — is an address, the port its MIDI is served on (51325 unless someone has changed it) and the channel its MIDI is set to: the same notes go down a socket to the desk rather than out of a port this computer had to open, so nothing has to be bridged and the desk can stay in the rack.

Beside the connection is the desk's model: an Allen & Heath SQ, an Avantis, or any desk that takes a note on to open a fader and a note off to close it. Naming the desk is what makes a scene recall work on it, because the arrangement follows the desk's own document rather than ours: an SQ is sent the NRPN mutes it reads instead of a note it would ignore, and an Avantis is closed with the note-on at a velocity in 01–3F, which is what its OFF is. The line under the row reads back what will be sent in those terms, and says so when the show drives more DCAs than the desk has — eight on an SQ, sixteen on an Avantis.

The desk's own buttons are the next row: GO button and BACK button, each a mute group. A console reports a key press only when the key has been given a console function, so a show's transport is a spare mute group rather than a MIDI note: pick the group here, assign that group to a key on the desk, and the key walks the scenes — GO to the next one, BACK to the one before, in the order the Scenes view shows them. A key press is a mute toggle, so either half moves the show. The desk's own report of where its groups stand primes the app rather than moving it, so a show opened onto a desk that was left with a group muted does not recall a scene by itself; and a DCA's mute is deliberately not read as a press, so a scene recall coming back off the desk cannot run the show.

Below it are the strips on the console and the DCAs they ride. A new show opens with twelve of each, strip n on DCA n — a wireless show is one mic per fader, so this is the arrangement it wants and not a guess — which leaves the tab holding the exceptions. A strip's DCA is a select in its row, so a chorus can share one fader; a DCA can be given an address or a note of its own where the desk numbers them differently, typed into the field that shows the derived one as its placeholder; and a DCA row reads back which strips it is carrying.

Cast is who is in the show: a performer, their role, and the strip their mic is patched to. Ensembles are named groups of them — the chorus, the band — and they are what a scene applies: applying one opens every member it holds, one press on the grid instead of a row of them.

What a recall sends

Only what changed. A DCA whose mics are all closed is closed, a DCA with any one of them open is opened, and a DCA already in the right state is not mentioned at all — a recall should be three messages, not a sweep of every fader. DCAs that no mic is routed to are left alone entirely, because the desk may well be doing something else with them.

Editing never moves the desk. When the scene on stage has drifted from where the desk was left, the view offers Apply to desk (N) with the number of DCAs behind, and waits. The all-closed column is the other half of the same idea: it is the press that shuts everything the show drives, which is what the desk wants between numbers.

Following the show

A recall can be a button press or a cue. Add a Scene cue from the toolbar's More menu, point it at a scene, and the desk moves when GO reaches it — pre-wait, post-wait, advance and triggers all behave as they do for any other cue. A cue that has not been pointed at a scene refuses rather than being read as “close everything”, and the run log carries the recall under the cue's own label, so the log reads as one story.

Edit and Done

The view always opens to run the show: recall, the all-closed column and Apply to desk stay live, and nothing else can be changed by a stray click. Edit is the deliberate press that gives the grid and the names back — cells, scene names, Add scene and + Ensemble — and Done hands the view back to the show with the line under the header going away with it. A stray click during a number cannot change who is open.

Which mode it was left in is not saved with the workspace: the file holds the scenes, and the view reopens ready to run them — including after a crash and recovery, which is exactly when you do not want to be one click away from editing the plot. The desk's own state is different: it belongs to the session, and a recall only remembers what the desk accepted, so a message that could not be delivered is reported and tried again next time.

Redundant playbackPro

Two machines run the same show: one driving it, the other standing by to carry it on if the first stops answering. Both run WinsLab with the same workspace open, and what passes between them is state rather than sound — which cue is running, how far into its file the engine has reached, what the operator has selected — so a machine that is standing by is ready to carry on rather than ready to start again.

Redundant playback, step by step is the walkthrough: setting a pair up, the status while nothing is wrong, a takeover as it happens on screen, what it carries and what it leaves behind, and a checklist for rigging it on the night. Read that one before rigging a pair; what follows is the reference.

The settings, and where they live

Everything is on the Redundancy tab of Settings, and it is this machine's own half of the arrangement rather than the show's: both machines load the same workspace file, so a role written into the show would be read as the same answer by both of them. These settings are kept on the machine, beside the license key — copying the show to the other machine does not carry them.

What a takeover carries

A partner that has said nothing for the stated silence is declared gone, and the alarm is raised once: in the Monitor panel, in the alarm chip, and in the run log. The audio cue the live machine was playing goes back on this machine's engine at the position it had reached, plus the silence since the last beat, and the operator's place in the show comes across with it — so the next GO fires what the live machine would have fired. Everything else is named in the run log rather than repeated: a MIDI or OSC cue has already gone out, a wait, fade or script was half-way through work that lived on the machine that died, and a cue in its post-wait had already finished. The walkthrough shows each of those in the log.

Who is driving

Each claim to the show carries a term, and the higher term is the one driving. A machine that comes back after a takeover hears a higher term than its own, stands down, and stops playing — it is no longer the sound, because the machine that took the show is already inside the cue. A machine that took the show over can hand it back from the same panel.

The honest edges are on the walkthrough's own page: both machines must have the same show open, unsaved edits are not mirrored, two machines set to Live both believe they are driving, and a silence cannot be told from a broken link.

Troubleshooting

A banner says the interface stopped unexpectedly

The window's process died and WinsLab restarted it, so the cue list comes back empty. The .wlab file on disk is untouched — open it again from WinsLab ▾ → Open Recent — and unsaved work is not necessarily gone: WinsLab snapshots it every 30 seconds while there are changes (see Workspaces), and the recovery bar offers the last snapshot back with Recover, including the cue the session was standing on. Recovered work counts as unsaved, so save it when the show allows.

A script cue never finishes

It is still running, and the show is waiting for it. Give the cue a shorter Timeout on the Script tab, or press STOP — both stop the script and release the show. A script cannot freeze the app while it runs, so the interface stays usable either way.

A network cue fails with "Failed to fetch"

The request never got a usable response. Three usual causes: the target server does not return CORS headers, nothing is listening on the host and port, or the URL is missing its scheme. Check the log for the exact message, and confirm the URL in a browser on the same machine.

A network cue succeeds but the show stalls

The server is not answering and the cue is waiting for its timeout — 5 seconds by default. Lower the timeout on the Network tab if the target should respond quickly.

A MIDI cue does nothing

Check the cue's port on the MIDI tab; if the cue does not name one, it falls back to the Default output set on the MIDI tab in Settings. On Linux, MIDI silently does nothing unless the native module was built with ALSA headers available.

A show control cue does nothing

Read the log line for the cue: it names what could not go where. A cue pointed at the show's desk needs a desk that takes MIDI — an OSC connection carries addresses, not show control — and one pointed at a MIDI port needs a port chosen (its own, or the Default output on the MIDI tab in Settings). On the receiving console, check that its Show Control device ID and command format match the cue's Device and For: both have to match before a console acts on a command.

An audio cue went silent after moving files

Audio cues store absolute paths, so moving the show or its audio breaks the link. Re-point the cue with Browse, or keep the audio beside the workspace and move the folder together.

A script cue does nothing

An empty script completes instantly and logs nothing but its start and completion lines. If the script is meant to produce output, look for an error line in the log — thrown errors are reported there and the cue still finishes.

GO skips a cue

That cue is disarmed, or it is a group child whose parent is running it. Disarmed cues are skipped by GO and excluded from groups.

The cue list looks empty after opening a show

If the file is not valid JSON, or opening it failed, Winslab reports "Could not open file" and leaves the current show in place. Validate the .wlab file in a text editor.

A trigger does not fire the cue

Three usual causes. The cue is disarmed — triggers respect arming. The OSC address is not exactly the one being sent (/eos/cue/12 does not match /eos/cue/12/fire). Or a MIDI trigger names a different input port from the one the message arrived on; the monitor lists every message with the port it came in on, which is the name to match.

The wireless panel shows no readings

The plot is there but no source is reporting. The Wireless tab in Settings reports what the wireless service is doing, including why a source failed. A source has to return JSON with a channels array — the shape is in Wireless and the mic plot.

Where are the error messages?

In the run log (the Log tab of the dock). Failures, HTTP statuses, and script output all land there. See Reading results.

Known limitations

These are behaviours and limits in the current build that differ from what the interface implies. They are listed so nothing surprises you during a show.

  • Fixed caps. The run log keeps the last 500 lines, a single script run emits at most 200 lines, and run-log messages and network response bodies are cut off at 4000 characters.
  • The script panel opens plain text only. A document over 1 MB, longer than 10,000 lines, or containing binary data — a PDF, a Word file, an image — is refused with the reason on screen instead of being rendered. That refusal is what stops a document that was never a script from taking the window down with it.
  • Saves are silent. Nothing confirms a successful save beyond the dirty dot clearing.
  • Group length is unknown for playlist and random groups. Their Duration column shows –, because the length depends on how the operator steps through them.
  • Listeners are listen-only. OSC input and MIDI input receive, show, and can fire cues — but WinsLab does not act as a MIDI or OSC destination that other software queries.
  • Wireless telemetry needs a source that speaks the documented JSON. Shure's System API, Sennheiser's receiver protocol and Dante's control protocol are not spoken directly, so a rack needs a small bridge between it and WinsLab — or the demo rack, which needs nothing. See Wireless and the mic plot.
  • One audio device at a time. WinsLab opens one output device and does not aggregate several into one; clock discipline across devices belongs to the operating system (an aggregate device) or to a Dante/AES67 layer. A rig with more channels presents them on one device.
  • Presence reports, it does not route. The network service notices that a device is there and when it leaves. Subscriptions, clocking and patching stay in Dante Controller or the device's own software.
  • Recording is not built in. WinsLab does not capture multitrack audio; a recorder runs alongside it. Triggers and OSC are how the two are tied together — a cue that arms the recorder, or a message from it that fires a cue.
  • A pair reads silence as failure. A machine that has stopped and a network that has stopped carrying its beats look the same to the machine standing by, so a partition can hand the show to the backup while the live machine is still playing it — both machines say so in their status and their log, and the live machine stops as soon as it is told. See Redundant playback.
  • Redundant playback carries sound, not everything. A takeover puts a playing audio cue back at the position it had reached and brings the operator's place in the show across; a MIDI or OSC cue that has already gone out, a wait, a fade or a script that was half-way through, and a cue that had finished and was waiting to hand over are all named in the run log rather than repeated. See Redundant playback.
  • Script cues are unsandboxed. Treat a workspace file as executable code.

Show-night cheat sheet

Setting up

  1. WinsLab > New, then name the workspace by double-clicking the title.
  2. Drag your audio files into the cue list.
  3. Add waits, fades, OSC, MIDI, network, and script cues around them.
  4. Group a run of cues if you want them to fire as one, or to place them on a timeline.
  5. Set Advance to On end on each cue that should hand over to the next.
  6. Save.

Running

  • Space fires the highlighted cue.
  • The highlight moves to whatever GO will fire next.
  • Escape stops everything; Shift + Escape stops with a fade.
  • If something looks wrong, open the Log tab and read the red lines.
  • With a pair rigged, the Monitor panel names the machine running the show and when the other one was last heard from.
